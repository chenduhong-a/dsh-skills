# 挑商品（shopping-guide）

## 触发场景

- 用户要买某类东西：「帮我挑一个 X」「推荐个 Y」「预算 N，买哪个」
- 用户给需求但没给型号：「主要用来 Z，有什么好的」
- 用户拿两三个候选问差异：「A 和 B 怎么选」
- 用户问某品类原理 / 值不值得买 / 为什么差价这么大

## 总流程（四步，顺序不可跳）

用户定调的方法：**先了解原理 → 再看商品用途 → 探寻买点与差异点 → 结合需求分价位提供建议**。跳步就会变成「报型号 + 报价格」的敷衍答案。

### 0. 先确定现状（2026-11-09 用户要求，不可跳）

在讲原理、挑商品之前，先把**使用者的现状**确认清楚，写成一段画像：

- **地域/气候**：常驻城市、当季温度区间、室内有没有空调暖气、湿度/雨季、通勤是否淋雨；
- **身体**：身高、体重、关键围度（腰/臀/大腿/脚长等），有无尺码踩坑史；
- **场景**：通勤方式与时长、久坐还是久站、使用频率、和什么搭配、洗晒条件；
- **预算与口味**：价格带、版型偏好、颜色禁忌、品牌偏好、能不能接受改衣/退换；
- **已有物品**：手上已有什么、这次缺哪一件、是否接受先买一条再补；
- **不确定项**：逐条列出来，逐个问用户（用 `ask_user_question`）或按最保守假设处理并在结论里注明。
- **品牌黑名单**：先问「哪些牌子一律不要」，用户说过的直接前置过滤。联想/Lenovo 全系（含拯救者/小新/ThinkPad）一律不推荐——2026-11-10 首推联想 100W PD 头被当场否掉；黑名单随用户明说更新，不自行推断。

现状没确认就开挑＝大概率挑错。用户原话（2026-11-09）：「先完整判断一下我的现状与需求吧，不然容易挑错」「商品挑选前先确定现状」。

**但「必问」不等于「全问」**（与第 2 节「不要为了追问而停住不动」不冲突）：只有能改变型号选择的那几项必须问到——预算区间、硬约束（尺寸/接口/不能接受的东西）、已有物品；喜好、颜色、品牌缺了就按最保守假设先给候选，边给边问。**字段按品类取**，上面那份是服装版的模子：数码取「已有设备与接口 / 系统与生态 / 主要用途 / 桌面还是携带」，家居取「房间尺寸与摆放位置 / 门宽与电梯 / 能不能打孔」，耗材取「用量与频次 / 存放条件」。

### 1. 先搞懂原理

在报价之前，先讲清这个品类**是怎么工作的、什么变量真正决定体验**。

- 找出 3–6 个物理/技术变量：例如耳机＝密封方式（半入耳/入耳）× 无线链路（蓝牙/2.4G）× 单元尺寸 × 麦克风阵列；扫地机＝吸力 × 滚刷形态 × 导航方式 × 基站能力。
- 讲清变量的**代价关系**，不只讲好处：半入耳＝不闷但低频与隔音天然弱；2.4G＝低延迟但占一个口、要接收器；大电池＝重。用户要能听懂「为什么便宜的那款注定差在哪」。
- 原理没搞清就先别报价；宁可先说「这个品类我先确认一下」。

### 2. 再看用途

把「品类」拆成「场景」，同一品类不同形态服务不同人。

- 问清（或从上下文推断）：**在哪用**（电脑/手机/通勤/运动/会议）、**用多久**（一局一小时 / 整天挂）、**和什么设备配**、**有没有硬约束**（戴眼镜、耳道敏感、不能入耳、必须能退）。
- 明确说出「哪些形态不适合你的场景」，比列一堆型号更有用。
- 用户没给场景时，先按最常见的 2–3 种场景各给一条判断，再让他选；不要为了追问而停住不动。

### 3. 探寻买点与差异点

把「厂商买点」和「真实差异」分开，这一步是选品质量的分水岭。

- 厂商买点常见噪音：灯效、联名、堆词（「AI 降噪」「电竞级」）、像素级参数、赠品。
- 真实差异通常只有 3–5 个，且往往带代价：延迟、续航、佩戴、麦克风、生态/App、售后。
- 对每个候选，找出**一条可验证的负面证据**（差评、论坛吐槽、测评里的但是）。
- 判据：如果两个型号的差异只体现在宣传语里，就告诉用户「这两款实际是同一档，按价格和售后选」。

- **不找「没短板」的机子**：让用户选「能接受哪个缺陷」，每个候选给 2–3 条线下验机项，比看评分有用。
- **参数自己换算成物理量再采信**：100W＝20V×5A，线必须 5A E-Marker（3A 线只到 60W）；多口同插会分功率、单口才满血；PD3.1 140W 要 28V 档，设备只到 20V/5A 时无效；品牌私有 140W（如机械革命）只能原厂头触发。换算不出来就写「未验证」。
- **读「分档/刀法」类内容逐条对齐主语**：每句话先问「说的是哪一档、哪个型号」，别顺读串行，把低档的评价安到高档上。

### 4. 结合需求分价位建议

- 按预算分 3–4 档（例如 200 / 400 / 800 / 1200+），每档 1–2 款。
- 每款写：**为什么是它**（对应哪条需求）+ **代价是什么**（续航/音质/缺货/生态）+ **怎么退**（有风险时）。
- 最后必须收口：一个明确首选 + 一句「什么情况下别买这款」。
- 价格跨度大时，说明「多花的钱买到了什么」，别只报价格差。

- **排序按缺陷接受度，不按评分**：续航 4h、底噪投诉、自营缺货比「几分」更能决定买不买。
- **每档附验机清单**：到货先验哪三项、什么情况直接退，写在该档建议后面。

## 调研纪律

- **样本要足、结论要慢**（用户原话，曾因样本不足被连续纠正三次）。型号要覆盖全，视频的**正文、简介、评论区**都要读，评论区只是旁证不是结论（见 `bili-transcript`）。先把候选铺满，再收口。
- 候选来源优先级：
  1. B站实测视频（口播 + **评论区**，评论往往比视频诚实）；
  2. 论坛真实用户（NGA / ZOL 点评 / 贴吧 / 知乎回答）；
  3. 导购站（什么值得买）交叉验证价格与历史价；
  4. 京东/淘宝**登录态**页面拿实时价（`browser-skill`）。
- **品类带宽**：先量「真正满足硬条件的有几款」——半入耳+2.4G 在售只有 4 款（2026-10-29 实测）。只有 3–5 款时如实说「就这么多」，向相邻形态扩列并**明确标注形态不同**（入耳式、开放式耳挂各列一组，写清「不是你要的形态」）；绝不用关键词堆砌的杂牌凑数——京东搜索页 49–98 元的「2.4G 闪连」多为改标题货。
- **证据分四层**，写结论时标清：官方标称 / 评测口径（含测试条件）/ 买家实测（带 rpid、评论楼层等可回溯门牌）/ 论坛个体反馈（标明是普遍问题还是个体风险）。每条负面都要能指回具体的人或帖，**指不回去的算没查到**。
- 官方与买家数据冲突时以多例买家为准，并**把冲突写出来**，不要只报一边。
- **价格可信度一条判据**：报价必须走完「登录态 → 自营有货 → 到手价折算 → 交叉验证」四关，缺一关不报价。①京东/淘宝的价格、库存只认**登录态**，未登录看到的是未登录价/推荐价；②**先确认自营有没有货**——机械师 TH70 官方 319 元、自营缺货，搜到的全是第三方 344–538 元加价，按页面价比较会得出错误结论；同一商品不同第三方店铺价差可达 200 元，报价只认自营或官方旗舰店；③**预售页读定金/尾款**——联想异能者 A7 页面 299，实为定金 10 元＋尾款立减 100 → 到手 199，且 0 评价＝全新品、风险自负；④页面价必须区分**券前/券后/Plus 价/百亿补贴**，什么值得买等导购站公开可读，只用来**交叉验证**历史价与口碑，不当成交价；⑤京东价格/评价 **API 都不可用**（p.3.cn DNS 超时、club.jd.com 回 application/octet-stream），只能读 item 页 DOM 的 `¥数字` 叶子节点，且必须带父级上下文区分日常价/政府补贴价/推荐位——item 页正文混入底部「为你推荐」低价，读价先确认标题与区块；切颜色变体后标题/主图/价格全变要重读，同系列不同版型可能是独立 SKU；评价池按款共用，总好评率不代表目标款；移动端 so.m.jd.com 会弹风控 `risk_handler`；⑥BrowserSkill daemon 掉线先跑 `bsk browsers`，不通就让用户重拉 daemon。
- **发布信息按机型逐个搜**：搜「机型名 + 发布/开售/价格」，比年度盘点准；百度百科正文容易被导航淹没，ZOL 有防刷验证页，别把抓到的首页当参数页。
- **比价数据源先看能力边界**：README 没写清「索引价≠结算价」的就别用，先用已知有货的商品做对照测试；价格类 MCP 已全不可用（best-price-mcp / cn-ecommerce-mcp 已删），2026-10-22 起**唯一可靠的在售价来源是 BrowserSkill 读登录态 Chrome**。

- **负面证据必须写**：赌的是什么、概率多大、怎么退。只讲优点的推荐等于没做。

## 交付形态

- **给建议前先讲原理与挑选要点**：每次给候选或报价前，先用 3–5 句说清「这类东西靠什么起作用、哪几个变量决定体验、你的场景该优先看什么」，再放图和价。用户 2026-11-09 明确要求：「给出商品建议前先简要跟我说一下原理和挑选要点以及理由」。
- 多个可选方案时，用 `ask_user_question` 弹选项卡（≤5 项、每项一句代价、推荐置顶），**正文不要重复罗列选项**。
- **先给实物图，要大、要能看清关键细节**：图按品类的关键变量选——服装配真人全身实拍（版型、垂感、裤长、收口），数码配屏幕点亮实拍 / 接口特写 / 整机正面，家居配放进房间的实景（看比例），耗材配包装与规格贴纸。大尺寸展示；不要平铺小图，也不要只截局部。每条配可点商品链接，让用户自己看版型/颜色。京东图取 `#spec-img` 主图或详情长图（imgzone/cms/pop 域，去掉 URL 末尾 `.avif` 即 jpg）。用户原话（2026-11-09）：「你上网页找几个给我看一下，我看看啥样」「图片太小了，整大一些，图片整穿上身的」「我的意思是穿在身上的图，不是单指上半身的图片」。
- 京东详情图滚动加载后按 `naturalWidth≥600` 收集；`#spec-list` 与 `#J_goodsList` 已失效，改用 `observe` 限量读。
- 报告结构建议：一句结论 → 对比表（型号/到手价/关键参数/一句话）→ 逐款细节（用 `<details>` 折叠，别用 CSS 单选 tabs——渲染层点不动）→ 口径与下一步。
- 文字优先，视觉卡只在需要对比或氛围时用；卡片内不用 Emoji。

## 边界

- **排除清单（用户明令，2026-11-10）**：**联想及其子品牌（ThinkPad / Legion 拯救者 / 小新 / YOGA / Motorola）一律不推荐**，电子产品这块尤其严格——候选里不出现，也不拿它做对比基准，直接跳过。用户原话：「电子产品一律不要联想的，写进记忆」——是「不要联想的」，不是「不买电子产品」。
- **商品事实不写进记忆库**（用户明令）：型号、价格、配置对比都不落库；只沉淀方法、渠道、口径这类可复用经验。
- 不替用户下单、不填支付信息；链接只作参考。
- 不做医疗/健康类功效断言；涉及安全（电池、承重、儿童用品）时把风险写清。
- 拿不准的参数写「未标/待确认」，不要编。

## 干完怎么算对（验收）

- 用户拿到了**能直接做决定的东西**：两三个候选 + 各自的关键差异 + 对应价位，而不是一堆参数罗列。
- 每个「更好」的判断都说了**好在哪个具体场景**（不做笼统的「性价比高」）。
- 拿不准的参数标了「未标/待确认」，没有编数字。
- 如果用户还在犹豫，说明缺的是**决策依据**（预算区间、使用场景、最在意的点），回去补问而不是继续堆参数。
