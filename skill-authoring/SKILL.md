# 写技能

一个技能 = 一份**给模型执行的手册**，不是给人看的文档。唯一目标：**一个全新工作区的新会话，只读这个技能，就能把这类活干对。**

## 0. 先分五种活

| 你在做 | 读哪几节 |
|---|---|
| 从零写一个 | 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 |
| 改已有技能（加步骤、换判据） | 2 → 5 → 6 |
| 不触发 / 总误触发 | 4 → `references/checklist.md` |
| 太长、要拆或并成复合技能 | 7 → 6 |
| 写完了要验收 / 落盘前自查 | `references/checklist.md` → §5 的「验收」→ §8 |

**什么时候动手写**：同一转换（同类输入 → 同一套步骤 → 同一类产物）做到第三次就该固化——第一次是探索、第二次是确认、第三次还出现说明它是常驻流程，不写就每次重新推一遍分支。回答这类问题时把决策树、每步判据、每步用哪个工具摊开，别只给主路径。

## 1. 加载机制决定一切

| 阶段 | 发生什么 | 对写作的约束 |
|---|---|---|
| 发现 | 扫技能根目录，解析 frontmatter | 头部格式错、路径层级错 → 技能**不会被加载**：宿主 warn and skip（有 warning 可查），模型侧没有逐技能的诊断，表现就是「静默消失」 |
| 目录 | 模型侧只渲染 `name` 与 `description`（description 可能截断）；`skills/list` 元数据另带其他字段 | description 决定模型能不能「想起」它 |
| 加载 | 命中后正文作为技能块进对话并常驻 | 正文越长越占上下文，且必须能独立读懂 |

三条铁律：

1. **description 是路由，不是摘要**——写不好等于技能不存在。
2. **正文是执行手册，不是知识库**——只写「模型不知道、且这次要用」的东西。
3. **加载是惰性的**——写进文件 ≠ 模型知道；不触发就等于没有。

## 2. 放置、命名、字段

扫描优先级（rank 值读 2026-11-26 的 `@dsh/skill-filesystem` README 与 `app.asar` 字段表；顺序仍以「当前有哪些 skill」的实际结果为准）：

| rank | 根 |
|---|---|
| 100 | `<项目>/.dsh/skills` |
| 200 | `<项目>/.agents/skills` |
| 300 | `customSkillDirs` 配置的目录 |
| 400 | `~/.dsh/skills` |
| 500 | `~/.agents/skills`（本机用户级技能都在这） |
| 600 | 内置（bundled） |

已知行为：项目根 = 从当前文件向上最近的含 `.git` 的目录，没有 `.git` 时回退到 cwd；`<dshHome>/skills` 扫描会跳过 `.system` 子目录；同名技能跨根时高优先级胜，低优先级同名只在它自己的根读取失败时补位；**一个根读取失败会隐藏该根其余可读技能**，不会逐条报错。

两种合法形态，**只扫根目录直属层级**：

```
<root>/my-skill/SKILL.md          ✅ 推荐（可带 references/ scripts/ evidence/）
<root>/my-skill.md                ✅ 扁平文件
<root>/group/my-skill/SKILL.md    ❌ 不会递归发现
```

| 字段 | 必填 | 要求 |
|---|---|---|
| `name` | ✅ | `^[a-z0-9]+(-[a-z0-9]+)*$`，与目录名一致 |
| `description` | ✅ | 模型可见的唯一路由信息；关键信息前置（目录侧可能截断） |
| `whenToUse` | — | 只进 `skills/list` 元数据（客户端 / `/` 菜单能看见），**不进模型侧目录**——模型侧只渲染 `name` + `description`，所以这个字段对触发没有帮助；触发词写进 description，别指望它补 |
| `metadata` | — | 自由元数据，加载与路由都不读；放给人或别的工具看的标记 |
| `disable-model-invocation` | — | 布尔；`true` = 只许手动调，不许模型自动加载 |
| `user-invocable` | — | 布尔；是否允许 `/name` 调用 |
| `author` | — | 本机惯例写所属线标识（`ZQY-LD` / `ZQY-LB`），**不带会话码**（2026-11-24 用户定，见 `~/.dsh/AGENTS.md` 第四节）。内核字段表里没有 `author`：未知键被容忍但无语义（2026-11-26 读 `@dsh/skill-filesystem` README 确认） |

布尔字段的合法写法：YAML 布尔（`true` / `false`）与大小写不敏感的 `yes/no`、`on/off`、`1/0`。值写成别的（如 `disable-model-invocation: maybe`）→ 整个技能被丢弃并给 warning；字段名写成 `disableModelInvocation` 这类 camelCase 则不被识别——等于开关没写，不报错。

**别抄市场侧字段**：`version`、`category`、`disableModelInvocation`（camelCase）写进去不会被识别。

### 2.1 交付前先验路径（唯一「写得再好也等于没写」的失败）

2026-11-20 实测：一个完全照手册写对的技能，因为被写到不在任何扫描根下的目录（作测试用），**永远不会被加载；宿主侧最多一条 warning，模型侧没有任何诊断**。所以写完先跑这个：

```powershell
$target = '<你放技能的那个目录>'
$roots  = @("$env:USERPROFILE\.agents\skills", "$env:USERPROFILE\.dsh\skills")
# 有项目级技能就再加：'<项目根>\.dsh\skills'、'<项目根>\.agents\skills'
if (-not ($roots | Where-Object { $target.StartsWith($_, 'OrdinalIgnoreCase') })) {
  "⚠ 不在任何扫描根下 —— 写进去也不会被加载"
}
```

不在根下只有三种正当出路：① 拷进真根；② 配 `customSkillDirs`；③ 明确声明「这是草稿 / 交付包，不可发现」。**沉默地写到别处是最坏的情况。**

路径合法后再验一次「真的被发现了」：开新会话问一句「当前有哪些 skill」，它能出现在目录里才算成功；出现在 `skills/list` 但模型侧没有，回头查 description 与 frontmatter。

## 3. 最小模板

> **本节的数值（300 字、四节、每节 5 条）全是示例，必须按你的场景重判**；照抄别人的判据是最常见的错误。

```markdown
---
name: release-note
description: "把 Git 变更整理成面向用户的发布说明。当用户要求写 changelog、版本说明、发版公告，或给出提交范围让你总结改动时使用。不用于内部技术复盘。"
---

# 发布说明

## 输入
- 提交范围：默认当前分支相对上一个 tag
- 目标读者：默认终端用户

## 步骤
1. 读 `git log --oneline <range>`，必要时看 diff 确认改动性质。
2. 按「新增 / 修复 / 兼容性变化 / 升级动作」归并，一条提交只归一类。
3. 删掉内部实现细节、临时分支名、凭据、issue 编号。
4. 影响不确定的条目标注「待维护者确认」，不自行推断。

## 停止条件
- 范围无法确定时，先问清范围，不要猜。

## 输出格式
- 按四个小标题分组；空节写「无」；末尾附「变更范围」一行。

## 验收
- 每条都能对应到具体提交；没泄露内部信息；读者不看代码就知道要不要升级。
```

## 4. description 怎么写

公式：**做什么 + 什么时候用（写用户真会说的话）+ 不用于什么**。

- 第三人称，不写「我可以帮你……」。
- 把同义词与英文都塞进去（changelog / 版本说明 / 发布公告 / release note）。
- 写出边界，主动排除相邻任务，减少误触发。**写完列一份「相邻任务排除清单」**：把这件活附近、用户确实可能说出口但该由别的技能（或不该由技能）处理的三五件事写进「不用于」，例如写发布说明要排除「提交信息润色」「执行发版流程」「版本号规划」「代码审查」。只排除「内部复盘」这类空泛词是不够的。
- 只做一件事；两件不相关的事拆成两个技能。
- 不要泛名：「办公助手」「需求处理」「代码工具」等于没有触发面。

**YAML 写法**：描述里有中文标点、冒号、`#` 或引号时必须包引号，双引号最稳：

```yaml
description: "把 Git 变更整理成面向用户的发布说明。当用户要求写 changelog、release note 时使用。不用于内部技术复盘。"
```

**长度**：目录侧对 description 有截断（`@dsh/skill-tool` README 写作 capped descriptions，**上限值未确认**），所以把最能识别这个技能的话放进前 40 字内。

| 差 | 好 |
|---|---|
| 帮助处理文档 | 把 Markdown 转成带目录的 PDF；当用户要求导出 PDF、排版打印、生成可分发文档时使用。不用于图片或表格分析。 |
| 代码审查工具 | 按团队规范审查 Java 改动，输出阻塞项与建议项；当用户给出 diff、PR 链接或要求 review 时使用。不用于性能压测。 |

自查一句：一个完全不了解你项目的人只读这段，能不能判断该不该用？

## 5. 正文怎么写

流程类技能按五段写，按序：**输入 → 步骤 → 停止条件 → 输出格式 → 验收**。

**这是本机技能库的共同骨架，不是所有 harness 的规范**：DSH 只要求 frontmatter + 正文，五段是为了让读者按同一顺序找到同一类信息。换 harness、或把技能交给别的系统时按对方约定，别把「必须有五段」写成普适要求。

**判据型技能不必凑五段**（红线清单、边界手册、纪律条款、症状→修法表）——强行套五段会产出「步骤：1. 注意安全」这类空段。替代要求：**至少有一张「什么时候停 / 怎么算干对」的清单**，两件事可以合并成一张（每行写「遇到 X 就停/改成 Y」），不必硬拆成「停止条件」「验收」两节。判据型示例：`html-card`（判据 / 三个渲染器与一个出口的选路 / 发卡前自检清单）、`doc-parsing`（先分诊再选通道 + 症状→修法表）。

- 只写模型不知道的：流程、领域约束、工具用法、质量标准、停止条件。
- 通识不写。「要仔细阅读代码」没有信息量。
- 必须执行的检查写成编号步骤，不要写成段落。
- **不写放权句**：「你可以根据情况灵活处理」会消解步骤的约束力。
- **命令必须自包含**：给出去的命令里不能有未定义的变量（写 `& $node x.mjs` 又不定义 `$node`，用户复制就报错）。要么给完整可跑的，要么写清「先 `$node = '<node 路径>'`」。
- **占位符可以用，但必须在本节内给出取值来源**：`<range>` 这种在「输入」里说明了怎么来的就行；跨节从没定义过的变量不许直接用。
- **路径用符号不用真名**：正文写 `SKILLS_DIR\foo`，不写 `C:\Users\某人\.agents\skills\foo`；实例路径只出现在末尾路径约定附录。
- 确定性计算放 `scripts/`，让模型调用，而不是每次即兴重写。

## 6. 落盘前自问的五类失效

这一节不是第 5 节的替代步骤，而是「写完了为什么没起作用」的检查单：写法见 §5，写多少见 §7。逐条问，每条都能用一个具体动作验：对照字面值、先造一个失败样本、grep 调用点、打开产物本身看一眼。

- **写了判据不等于判据生效**：判据写「分四类」，代码里按阿拉伯数字 `4` 判，或反过来——对不上时规则静默失效，跑起来谁也不报错。写完对照代码里的字面值核一遍。
- **校验器要先造一个失败样本**：`check --deep` 连续几轮都报「一致」不是好消息，可能它比的东西早就不存在了。先手工改坏一处，看它报不报。
- **验证工具会跟功能脱节，而它每轮都报绿**：某项目的 selftest 19 步全过，新加的 `--date` 参数一跑就 `TypeError`——测试从没碰过它。加功能时同步加断言，判据写「这个参数真的被调用了」，不是「脚本没崩」。
- **看起来在工作的死代码**：某模板系统里的 `\answerhead` 宏定义了十几版，从没被任何模板调用，改它当然「没反应」。改之前先 grep 调用点，0 命中就是在改死代码。
- **「错了但不报错」有四种形态**：同名产物静默覆盖、空产物（0 字节 PDF）、参数越界被默认值吞掉、统计口径与展示口径不一致。四类都只能靠「产物本身对不对」发现，靠退出码永远发现不了。

## 7. 体量与分层

| 层 | 放什么 | 建议体量 |
|---|---|---|
| `SKILL.md` | 路由表、跨篇铁律、脚本表、基线 | 本机约定：常见 50–250 行（12 个 user 技能的分布见 `evidence/measured.md`）；按下方三条判，不按行数硬切 |
| `references/<篇>.md` | 步骤 / 判据 / 症状→修法 / 红线 / 命令模板 | 每篇 ≤ 200 行 |
| `evidence/<篇>.md` | 带日期的实测、事故字节数与报错原文、版本沿革、试错过程 | 不限，正常执行不读 |

**依赖别只写「见某技能 / 见某插件文档」**：指路在对方升级后会静默失效（改写、改名、删节都不报错，只是查不到），技能自己的判据要内联。判据：读者只拿这一份能不能把活干对——「要可靠就内联，要追踪新版就补指路」，指路当补充，正文留可执行的那一份。

**行数只是提示，不是验收线**：不存在「必须 ≤100 行」——按它卡只会逼人删判据。真正该看三条：

① **主题是否单一**——一个技能只做一件事，两件不相关的拆两个技能；
② **有没有大量只用于复现的实测数字**（字节数、行号、报错原文、版本沿革）——有就拆 `evidence/`，正文只留指针；判据是「只读 SKILL.md + 相关 references 能不能把活干对」，能拆就拆，不能说明缺的是判据不是证据；
③ **读者要顺序读完吗**——要（手册类、流程类），别动行数，按主题拆成复合技能；不要（查字典式），拆 `references/`。超过约 250 行必答这一问，**200–250 之间是灰区**，同样用这一问定方向，不按行数硬切。

落盘前的四级验证与反模式速查在 `references/checklist.md`。

**复合技能**：流程很多、彼此独立时，别写成一个巨型 SKILL.md，改成「一个技能目录 + 多篇 references」，主文件只当路由：

```
dsh/
├── SKILL.md            # 选篇表 + 跨篇铁律 + 脚本表
├── references/         # ops.md / plugin-dev.md / internals.md / selfcheck.md
├── evidence/           # 同名四篇
└── scripts/            # 随技能走的脚本
```

**「拆」默认指拆 references 篇，不是新建同级技能目录**（2026-11-21 踩过：把 `doc-parsing` 的 Office 部分拆成独立的 `office-parsing`，用户当场指出违反本规则）。判据：两类内容是否共用同一套工具与同一批前置判断——共用（PDF 与 Office 都走 `doc_*` 工具、都先分诊）就是一个技能两篇；只有「别人要单独拷走这一份」时才另写独立技能。

**跨机器可移植（要能分享出去）**：技能是给别人或换台机器用的，两条硬要求——① **零本机绑定**：绝对路径、本机课名、会话码一律走 `config.json` 或文末路径约定，正文只写符号（`SKILLS_DIR\foo`）；外部依赖（知识库 / StudyHub / TeX Live / PDF 解析器）标成可选，缺了要在执行处明说降级到哪一步，不许静默失败。② **吸收别人的技能只借机制不搬实现**：读它的机制（顺序、判据、失败面），按自己的工具链重写；照抄实现会把它的坑一起搬进来。

**改造已有技能用原地替换，不另存分支**：老稿先备份到 `work\_tmp`，正文直接改原文件。「留一份分享版」会让两版长期分叉（改了一版忘了另一版），要分享时另发独立技能，而不是在同一个目录里养两个版本。

**改完扫旧名**：改名或合并后至少扫六处——目录名、frontmatter `name`、description、正文交叉引用、`references/` 里的指路、脚本里的路径常量。命中分三类：该改的旧名、带日期的历史证据（保留）、同时认新旧名的兜底逻辑（保留）。把「看起来像旧名」全改掉会破坏证据与兼容层（2026-11-18 合并 `doc-parsing` 漏 4 处；2026-11-20 审计 13 处命中只有 4 处该改，见 `evidence/measured.md`）。

**改完先提交**：`~\.agents\skills` 是 git 仓库（2026-11-26 实测 123 个文件 / 1.33 MB / 24 个 commit，`.gitattributes` 统一 LF）。改完先在目录里 `git add -A && git commit -m "…"`——这是「回退只准 `git restore`、不许模型重写一份看着一样的」的执行基础：没有 commit 点，回退就只能靠重写，而重写正是这类事故的成因。远端、代理、凭据助手属于仓库运维，不写进写作手册：要推远端时按 `~\.gitconfig` 与当前网络现场确认（诊断三步见 `windows` 技能）。

## 8. 独立子代理验收

自己复读只能确认「我写的我懂」，抓不到「我知道但没写下来」的前提。交付前让一个没参与写的子代理做一次最小任务：

- 任务书只给「读 `<SKILLS_DIR>\<技能名>\SKILL.md`，按它完成 <最小真实任务>；只准读这个目录，缺什么照实说」，**不给**你的思路、期望产物或示例答案。
- 看三样：①它在正确时机加载了技能吗（没加载＝description 或路径有问题）；②它执行时要不要回头问你（要问＝判据缺失或命令不自包含）；③它的产物与你手做的差在哪。
- 它报「缺 X」时先修技能，别在对话里口头补——口头补的那句下一次不会存在。
