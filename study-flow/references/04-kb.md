# 04 · 建一个能查页码的知识库（通用流程）

**这一篇只讲怎么建，不讲我们库里有什么。** 你可以完全不用它——没有库一样能带课（`07-environment.md` 第五节），只是「查原文」只能按章节抽页，不能跨全书检索。

## 一、先判要不要建

| 情况 | 要不要建 |
|---|---|
| 只有一两份 PDF，讲到哪读哪 | **不用建**，`doc_text` 按页抽就够 |
| 材料多（三五本教材 + 十几讲课件），经常要「哪一页提过这个概念」 | **建** |
| 要出章节总结 / 依赖图，需要全书知识点分布 | **建** |
| 要跨课检索（「我哪门课里讲过 XX」） | **建** |
| 扫描件、要 OCR 才有正文 | 先 OCR，再决定建不建（见 `05-materials.md`） |

建的代价：一本 300 页的书，有文字层约 1–2 分钟；扫描件要 OCR，约 1–6 秒/页。**不要为了「建完整」先 OCR 整本**——先建头几讲要用的章节，讲到哪建到哪。

## 二、库形态三选

| 形态 | 适合 | 优点 | 缺点 |
|---|---|---|---|
| **SQLite + FTS5**（默认） | 大多数情况 | 单文件、可备份、全文检索快、能存页码与章节 | 要写一点 SQL 或用一个 CLI |
| **Markdown 目录** | 想直接看、想用编辑器搜 | 零依赖、肉眼可读、git 友好 | 全文检索靠 `rg`，页码要自己写在一行里 |
| **向量库** | 语义检索（「讲得差不多的地方」） | 模糊匹配强 | 要模型、要服务、不能给精确页码；本书这类**不需要** |

**建议**：先用 SQLite + FTS5；如果只是自己翻，Markdown 目录也够。**不要一上来就向量库**——它会让你以为在检索，实际答不准页码。

## 三、最小 schema（SQLite）

```sql
create table courses (id integer primary key, name text unique);
create table docs (
  id integer primary key, course_id integer, rel_path text,
  pages integer, source text          -- source: pdf / ocr / ppt / photo
);
create table items (
  id integer primary key, doc_id integer, page integer,
  title text,                           -- 这一页/这一节的标题
  section text,                         -- 章 › 节
  text text                             -- 正文（公式尽量保留 LaTeX）
);
create virtual table items_fts using fts5(text, title, section, content='items', content_rowid='id');
```

**一条记录 = 一页**（或一节）。不要一条记录塞整章——页码会丢，检索命中也没法定位。

**读 `kb.sqlite` 的脚本先 `pragma table_info(docs)` / `pragma table_info(items)` 看真实列**，别照旧脚本推断：`docs` 表**没有 `title` 列**，凭印象写 `select title` 会报 `sqlite3.OperationalError: no such column: title`，只能改 `select rel_path` 再按文件名推标题。

## 四、入库五步

1. **判文字层**：`doc_info` 看有没有可抽文本。有 → 第 2 步 A；没有 → 第 2 步 B。
2. **取文本**
   - A（有文字层）：`doc_text --pages all`，或直接用 Python（`pypdfium2` / `pypdf`）逐页抽。
   - B（扫描件）：先 `doc_ocr`（或你自己的 OCR），缓存下来再读；**不要每次重跑 OCR**。
3. **清洗**：去掉页眉页脚重复行、连续空行、控制字符、私用区字符（`U+E000–U+F8FF`）；公式里的上下标乱序**不要硬修**——保留可读部分即可，页面上以原图为准。
4. **一页一条写进去**：`page`、`title`（这页的大标题）、`section`（`章 › 节`，没有就留空）、`text`。
5. **重建索引**：`insert into items_fts(items_fts) values('rebuild');` —— **手工写库必须做这一步**，否则检索一条都命中不了（这是最常见的坑）。

## 五、三条验收（建完立刻验）

1. **三词命中**：从要讲的章节里挑三个不同的专有名词，各自检索都有命中，且第一条落在合理页码。
2. **页码对得上**：随机抽 3 页，用 `doc_render` 出原页图，和图里内容比对——**页码错位是最隐蔽的错**（书页 vs PDF 页常有偏移，比如书页 + 14）。
3. **空页率**：`select count(*) from items where length(trim(text)) < 20` ÷ 总条数。> 15% 说明抽取有问题（多半是扫描页没 OCR）。

三条过不了就不要拿它查原文——先修数据，不要修检索参数。

## 六、用脚本建（`scripts/build_kb.py`）

先定 `$PY`（见 `SKILL.md` 第六节；本机裸 `python` 是应用商店占位程序，跑不动）：

```powershell
& $PY scripts\build_kb.py --db mykb.sqlite --course 课程名 --pdf "教材.pdf" --pages 1-120
& $PY scripts\build_kb.py --db mykb.sqlite --course 课程名 --dir "课件_pdf" --pattern "第*.pdf"
& $PY scripts\build_kb.py --db mykb.sqlite --list            # 看建了什么
& $PY scripts\build_kb.py --db mykb.sqlite --check 声子 晶格 热容   # 验收：三词都得命中
```

脚本行为：只处理**有文字层**的 PDF；扫描件会明确报「需要先 OCR」并跳过（OCR 走 `05-materials.md` 的工具，本脚本不内置 OCR）。写完自动 rebuild FTS。`--check` 走 `LIKE '%词%'` 而不是 FTS——原因见下一节。

**本技能只带这一个建库器。** 下面第七节的查询 CLI 是可选的：使用者在 `config.json` 里配 **`kb.cli`**（**嵌套键，不是顶层 `kb_cli`**——顶层那个没有任何脚本读），指向他习惯的查库入口（`.cmd` / `.py` 都行；本机实例是 `C:\deepseek\study\_kb\kb.cmd`，**不是** `_kb\kb.py`），没有就用 SQL 直接查。别把查询 CLI 当建库器用——它不做抽取，也不建 FTS。

## 七、查询接口（没有 CLI 就用 SQL）

```sql
-- 按词找页码（中文子串）
select d.rel_path, i.page, i.title
from items i join docs d on d.id = i.doc_id
where i.text like '%声子%' order by i.page limit 10;
```

**中文检索要注意**：FTS5 默认的 `unicode61` 分词器**不切中文词**——一整段汉字段算一个 token，所以「薛定谔」查不到「薛定谔方程」这句里的那三个字。两条路：

- 建表时用 `tokenize='trigram'`（SQLite 3.34+）：支持 ≥3 字的子串匹配，`items_fts match '薛定谔'` 可用；
- 或者干脆用 `LIKE`（几千到几万条秒回）：两三个字的词也能查，最省事。

`build_kb.py` 的 schema 用的是默认分词（给英文和整词检索用），验收走 `LIKE`——这不影响别人换成 trigram。

**判据**：能回答「这个概念在哪本书哪一页」——答不出就是库没建好，回去看第六节。

## 八、维护

- 加了新书就再跑一次第 4–5 步（增量），不要重建整库。
- 库是**派生数据**：源头 PDF 变了（新增讲次、重新裁切），对应 doc 要删了重灌，不要留着旧页。
- 备份就是复制那个 `.sqlite` 文件；不要把它放进 git 仓库（体积大、二进制）。
- 库只出 **CLI / SQL 查询**，不做网页版：界面不是需求，「开课时有底座、提问时调得到」才是。曾经写过一个 2000 多行的 serve，最后全删了。
