# 派子代理与跨会话协作

> 路径符号（`NODE_BIN`、`DSH_HOME`、`SKILLS_DIR` 等）见 `SKILL.md` 附录；带日期的实测明细在 `evidence/measurements.md`，本篇只留判据与案例。

两条线：**往下派**（子代理）看任务书与写域，**横向交**（另一个会话）看留痕与交接件。共同点：它们都看不到你脑子里的上下文，写下来的才算数。

## 判据：这次自己干，还是派出去

派出去，满足任一条就值得：

1. 活长、要读一大片材料，但你只需要结论——读过的文件不必留在自己上下文里。
2. 需要「敢乱用」的探索性测试：构造空 PDF、坏 schema、`force` 连击、并发双路这类人类懒得试的输入。
3. 两条互不依赖的验证线可以并行：一条黑盒真调，一条静态扫（grep 旧名、读参数表、查输出上限）。黑盒测不到「过时文案与废弃参数」，静态扫能补。
4. 写域互不重叠的批量活：A 改一个目录，B 改另一个。

自己干，满足任一条就别派：

1. 一两步就能做完的短活。派出去的开销比省下来的多。
2. 任务书六样里有两样以上说不清——说明活没定义好，先定义再派；硬派出去就是让它猜。
3. 需要本会话上下文才能判断，或者要现场问用户拍板。
4. 验收等于把活重做一遍，而且产物只有一两行结论。

同一路已经失败两次：第三次之前换维度——换思路，或者换执行者。换执行者不是把同样的命令再发一遍。

实测参照：2026-11-09 派独立 agent 测插件，17 分钟交回 12 个 BUG，其中 1 个是主会话审了 1290 行没看出来的严重 bug（prefetch 结果被 IIFE 丢弃）。值得派的是这种「另一个人愿意往坏里试」的活。

**能拆就拆的理由**：读大量材料、批量核对、逐条梳理、独立取证交给子代理，主线只留结论——上下文一长，无关内容会稀释判断（2026-11-18 用户定规：「避免上下文过长，污染，影响智力」）。几屏能看完的不必拆；要跨多轮连续判断、或产物要现场反复调试的留在主线。

**大规模梳理的具体做法**：按层导出 md（含 id/字数/命中/日期），每份一个只读子代理，任务书要求按「方法论 / 技术判据 / 事实 / 一次性事故 / 偏好」分类并逐条给「编号 | id | 类型 | 去向 | 理由」，写明「逐条覆盖不许抽样」；主线负责归并同名建议、排冲突、落地。

## 任务书六样（缺一样就别发）

写之前先读对方要用的那份文档（插件的 `SKILL.md`、工具说明），核实能力边界，别凭对自己环境的印象写。

1. **路径与工具名**：源码/素材的完整路径，全部工具名。不要让它自己找。
2. **两条测试通道**：黑盒（真调工具）；白盒（`import lib/main.js` + 假 `ctx.tools.register` 收集工具后直接 `execute`，绕开宿主，能注入坏参数）。
3. **运行环境**：本机 node 用 `NODE_BIN`（见 `SKILL.md` 附录路径约定；实测不在 PATH 里），给绝对路径，别让它自己 `where node` 猜。
4. **写入范围**：素材只读；产物只许写某个目录。派任务时同时登记 `team_task_create` 的 `writeScopes`。
5. **报告格式**：BUG 编号 / 严重度 / 复现步骤 / 期望 / 实际 / 证据路径。
6. **升级通道**：发现严重问题先单独发消息，不用等全跑完。

模板：

```text
目标：<一句话；成品是什么、放哪个目录>
路径与工具：<源码/素材路径>；工具名：<全部>
两条通道：黑盒 <怎么真调>；白盒 <import ... + 假 ctx.tools.register 后 execute>
运行环境：<NODE_BIN 的实际路径>
写入范围：只许写 <目录>，其余只读
报告格式：编号 / 严重度 / 复现步骤 / 期望 / 实际 / 证据路径
升级通道：发现严重问题先单独发消息
验收：<什么算完成，谁看哪一份产物>
```

判据：**任务书写完，自己能不能照着它从零复现一遍**；不能，就是还有歧义。

## 先复用再新建

2026-11-19 用户定规：「子代理优先建立可复用的，并且用的时候也优先用可复用的」。动手 `subagent` 之前先 `list_agents`，有对口角色就 `send_message` 派给它，别加编号新建第二个（本机曾出现：`doc-auditor` / `script-auditor` 已存在且闲置，却又建了 `doc-auditor2` / `script-auditor2`）。

判据：这活半年内还会再出现吗？会，就固定成一个人并复用；`subagent` 只给一次性、边界明确、不必保留的活。角色名用稳定职责名，不要 `xxx2`。

## 怎么切分（写域不重叠）

1. **首选按文件切**，其次按目录，最后才按职责。按职责切同一文件时，只能一人写、一人只读评审。
2. 同一文件、同一目录、同一存储，同一时刻只有一个写者。两个代理同时「顺手修一下」同一个文件，后写的会覆盖先写的，而且**没有冲突提示**——脚本和格式化工具写文件不做冲突检测，改完才看得到谁被吃了。
3. 切分维度对照：

| 切法 | 怎么切 | 适用 |
|---|---|---|
| 按文件 | A 改 a.js，B 改 b.md | 首选，文件之间不互相引用 |
| 按目录 | 各自一个子目录 | 产物多、结构清楚 |
| 按职责 | 一人写，一人审 | 同一文件必须两人碰 |
| 串行 | 排队写同一存储 | 记忆库、共享脚本、回信文件 |

4. **共享面不是谁都能写**：`memory_mail` 信件、共享脚本（`transcript.mjs` / `batch.mjs` / `opus-read.mjs`）、记忆库、profile/插件/配置。归属看**谁维护这份文件**，不看内容写给谁。
5. **同一存储的写必须串行**：并行 `memory_remember` 可能返回同一 id、静默丢内容或生成重复条目；写完 `memory_read` 回读。id 前缀会撞，记完整 id。
6. **并发上限 ≠ 能并行加速**。日志写 `Request concurrency limited to 3`，只说明允许 3 个请求进来，不说明能同时算 3 个：实测同一批 8 页、batch 2，3 路并发 25 秒，串行 22 秒，并发更慢（服务端顺序排队，3 份 37 MB 文件互相争 CPU）。派多个代理前先问一句：它们的瓶颈是不是同一个服务、同一个文件、同一把锁。
7. 重叠时改切分，不要靠自觉。`writeScopes` 只登记不断言，真正的约束写进任务书第 4 条。
8. **代理数量本身要问一句**：用户 2026-10-22 提醒过「你的子智能体是不是太多了」。派 N 个之前先数三样：每个的产出是否独立可验收、它们的瓶颈是否同一个（同一服务 / 同一文件 / 同一把锁）、合并成本是否低于自己干。超过 3 个就要能一句话说清各自不可替代的理由。
9. **审查类任务按域派两个只读代理，比派一个综合审查狠**：实测三轮共 35 条，综合型代理往往只报表层、按域代理能挖到本域深处的边界。两个都只读、写域为空，主线合并去重后再抽查。

## 验收与抽查

1. 抽查不是逐行重做，也不是「找错」。先列出**「它可能对但我不敢信」的点**，通常 3~5 个：关键公式、关键数字、关键判断、跟常识不符的地方。每个点找一条独立证据（原图、原文、实测输出、源码行）。
2. **「与常识不符」有两种可能**：真错了，或者有你不知道的写法。改任何人的产出（哪怕 AI 的）之前，必须有**一次独立证据**。案例：公式转录出现 `ψ = ψ + O₁`、`O₂ = O₂ + O₁ = O₁`，看着像把零元 0 读成了字母 O；读原图后确认老师就是用 O 表示零元，并借这个式子证 O₁=O₂——代理没错，差点把对的改成错的。
3. **报数前重读**。说「现在有几个 / 改完没有 / 文件多大」，重读文件再报，不要凭上一轮记忆：别的会话可能同时在改同一文件。报出的每个数都要能回到具体文件（路径 + 行数/字节数）。
4. 报告先按格式核对：缺「证据路径」的 BUG 不算数，先复现再采信。严重度要重排一次——它标「低」的可能只是它没看懂影响面。
5. 结论性字段不信 verdict，只信事实清单：点开行号/文件复核一遍再转述。
6. 抽查覆盖面上限：每个写域至少看一份完整产物，其余抽样；「严重」结论一条不跳。
7. **抽样不能只用自己挑的样本**——只抽「我以为有问题的地方」是在验证自己的偏见，没抽到的地方永远不知道有没有错。随机抽一部分 + 按写域全覆盖，两类样本大致各半；只验疑点的抽查，报告里要写明「未做随机抽样」。
8. **成员的建议与用户既有要求冲突时，以用户为准并在报告里显式说明**：写「A 建议 X，但用户 2026-11-XX 定过 Y，按 Y 执行」，别默默折中——折中出来的第三版谁都认不出。

## 子代理验收（干完怎么算对）

**两条**：①它拿到的是自包含任务书（不依赖本会话上下文）；②产物有具体数字（行数、字节、md5），不是「已完成」。声称「草稿已写入」的，要自己核字节数、行数、`##` 节数、frontmatter。

## 跨会话交接

### 交接件（给接手的新会话）

新会话自动继承记忆库（按 cwd 的 `.dsh-mind\memory.db`）、磁盘产物、插件与技能配置；**不继承对话历史**。所以交接件要装的是：结论、路径、下一步。

1. 位置：`C:\deepseek\上下文归档\<session-id>-<角色>-<识别码>.md`（2026-11 起的规范名），新会话第一句就让它读。
2. 给不懂技术的用户的助手提示词，六节结构有效：
   1. 开工自检：先看环境与工具面，再动手。
   2. 装插件：体积代价、确切命令、重启与验收步骤、工具没出现时的排查顺序、别反复重试同一招。
   3. 核心工作流：把专业步骤写死，注明「必须用 X、禁止用 Y」。
   4. 怎么跟用户说话：说人话、一次只让做一件事、给按钮不给填空题、命令自己跑别让用户复制粘贴、出错先说卡在哪再给简单办法。
   5. 红线：未同意不装不改不动文件、隐私不落盘、装完必须重启验收、不糊弄。
   6. 退路：用户不想装时的降级方案，并说明效果打几折。
3. 写前实读对方的 `SKILL.md` 核能力边界。交接件写完就不再改；接手方以文件现状和会话日志复核，不以交接件为准。
4. **每条路径与数字当场核**：交接件里写的文件、目录、行号，落笔前 `Test-Path` / `Get-Item` 逐个确认存在，写「69 行 / 5,815 B」这种数字当场量一遍——路径失效的交接件比没有更糟，接手方会照着一个不存在的位置找，还以为是自己的问题。
5. **用户要「改动建议」就给一份 .md**（2026-11-13 原话「改动建议输出一个 .md 文件」）：别散在对话里，落成文件他才好逐条批。

### 留痕（改了共享面）

1. 触发范围：删/移共享目录、改共享脚本、改记忆库（归档/删除/批量修改）、改 profile/插件/配置、B站工具链变更、浏览器 daemon 启停。
2. 落点：**`memory_mail` 信箱**（`post` 时 `scope=global` 写 `C:\deepseek\.dsh-mind-global\mailbox\`，`scope=local` 写 `<cwd>\.dsh-mind\mailbox`），每人按发件码区分。只投自己的信；不 archive / 改写别人的信。**2026-11-25 核对：旧机制 `C:\deepseek\work\_relay\` 目录已不存在**，本节其余各条（当轮写、三样写清、身份码、压缩校验）对信箱同样适用。
3. **当轮写，不事后补**。把「写一节留痕」当成操作步骤的一部分，与改库、删文件同级。事后补是欠账。
4. 三样写清：做了什么 / 影响范围 / 回滚方式。
5. 每节末尾带身份码；没码的节不算本人写的。身份码不跨会话沿用、不自动认领——要新建、沿用或更换，先问用户。
6. **跨工作区传话写自己文件**，标题注明收件人（如「致图书管理员（LB-5BE758-B5D8）」）。历史机制（`_relay` 时代，已废止）：2026-11-09 起 relay 只作单向通知，消息由用户在两边转述；**现役做法是用 `memory_mail`**，附一段可复制话术，不要依赖轮询。
7. 维护：被证伪的结论只留一行 + 修正标记（已证伪/不完整/被取代），支撑细节删掉；定期压缩（历史数据（`_relay` 时代）：from-other 16.7 KB→3.9 KB、from-lead 121→37 行）；压缩后回读校验行数、字节数、小节标题。
8. 接手别人改过的共享件：先 `memory_mail list` 找改者那封信的说明（改了什么/为什么/验证/回滚/影响面）→ 核对代码实际改动 → 跑真实调用 → 查缓存交互坑。（2026-11 前的旧留言在 `_relay` 里，该目录已于 2026-11-25 前后删除，不要再去翻。）

### 两者的边界

1. 交接件回答「接手的人怎么把活干下去」，读者是新会话；回信回答「我动了什么，你会受什么影响」，读者是并行的另一个会话。
2. 不要把交接件当回信投进别人的文件，也不要把回信当交接件交给新人——前者越界，后者缺步骤。
3. 一件操作可能两样都要：改了共享脚本 → 当轮回信写影响面；这次改动要交接给新会话 → 另写一页交接件。两份各自写全，不许写「参见」。

## 常见失败

1. **把「写给谁」当成「谁维护」**——回信追加进了对方维护的文件，连自己以前误写进去的旧节也顺手改了。判据：落笔前问这份文件平时由谁改；不是自己，就写自己那份，标题写收件人。
2. **抽查变成找错**：看到与常识不符就改，把对的改成错的。先取一次独立证据再动手。
3. **凭记忆报数**：别人同时在改，数字早变了。重读再报。
4. **任务书缺写域**：代理「顺手」改到共享文件，或把产物丢在根目录。第 4 条与 `writeScopes` 两处都写。
5. **任务书缺证据格式**：交回「有 3 个问题」但复现不了。第 5 条先定死。
6. **假设并发更快**：日志写 `concurrency 3` 也不代表能同时算，实测 3 路比串行慢。派多个代理前先找共同瓶颈。
7. **并行写同一存储**：`memory_remember` 并行会撞 id、静默丢内容。串行写 + 回读。
8. **只写对话不写文件**：留痕没落在回信里就等于没留；当轮不写，事后补是欠账。
9. **交接件写成技术笔记**：读者是另一个 AI、服务对象是不懂技术的人，六节缺一节就会越权或让用户自己复制粘贴。最常缺的是「红线」和「退路」。
10. **新会话自动认领旧身份码**，或沿用别的会话的码：串味。码只认用户确认或本会话历史。
11. **回信只增不压**：十几 KB 的文件，读的人要付全价。按维护规范压缩，压缩后回读校验。
12. **改完不找原审阅者复看**：让同一个审阅者看它自己上轮意见的落地，比换一个人更狠——它记得当初为什么提，能立刻指出「这条你说改了，但改的是另一处」；换人只看结果，容易放过「改了但没改对」。
