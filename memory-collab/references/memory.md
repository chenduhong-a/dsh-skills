# 记忆与准则维护

> 场景：写一条记忆、整一批记忆、给记忆库体检、改准则文件、搬记忆目录。全部动作只对当前工作区的库生效；跨工作区一律走文件与留痕。

## 库位置与状态

- 每工作区一份：`<cwd>\.dsh-mind\memory.db`（2026-11-20 起用 meow-mind；旧 `.dsh-meow` 只作回滚保留，别再写）；**九层表**（soul/user/project/fact/lesson/principle/topic/rules/todo，2026-11-23 加了 `principle` 经验准则层），另有**时间线五表** `episodes`／`phases`／`decisions`／`personas`／`persona_traits`，以及 `events`／`memory_vectors`／`memory_evidence`／`memory_relations`／`memory_versions`／`memory_feedback`，**没有 `memories` 表**（2026-11-21 起多一张 `todo`）。
- **两库**（2026-11-21 起）：另有一份全局库 `C:\deepseek\.dsh-mind-global\memory.db`，放跨工作区成立的本机知识；写入时 `memory_remember` 的 `project` 填「全局」即落那边，其余工具按 id 自动定位。判据与禁区见本文「两库判据」。
- 版本流水不进记忆层：用插件内置 change_log 表记（`memory_log` 的 add/list/remove/stats，或斜杠 `/log [关键词]`），别建独立文件；记忆只留当前基线与选型判据。
- 全局目录 `~\.dsh-mind`（日志、窗口账本）；切换落 `$DSH_HOME\storages\meow-mind-home.json`。
- 查数用 `node:sqlite` 只读打开：`select status, count(*), sum(length(content)) from <层> group by status`。**六态**＝`observation`／`evidence`／`candidate`／`memory`／`review`／`evolution`（`evolution` 计划退役：2026-11-23 实测两库 0 条，演进其实由 `memory_versions` 记）；**旧三态映射**：`active`→`memory`、`stale`→`review`、`archived`→`review`（旧库里的 active/stale/archived 字样只出现在 `.dsh-meow`）。

## 判据

先分四类再动手，分错类后面每一步都错。

| 触发 | 类型 | 动什么 | 汇报 |
|---|---|---|---|
| 一条新事实或教训；用户说「记住」；出现「以后…都…」「下次你说 X 我就 Y」 | 写一条 | 新增一条或 update 一条 | 当轮一句 |
| dream、合并重复、拆超长、批量归档、插件改名或合并后扫旧名 | 改一批 | 多条，串行 | 收尾给回执 |
| 「体检」「自检记忆库」「清理过时条目」 | 体检 | 全库四类问题，当场修完 | 报告带前后数字 |
| 搬记忆目录、动 memory_home、换盘 | 迁移 | 全局数据目录；库本体另行确认 | 动手前说清代价 |

三条总纲：

1. **授权边界**：用户已授权「体检 + 清理 + 拆分」属常规维护，可直接执行、事后汇报（2026-09-30 原话「你觉得怎么改好就怎么改，不用一直问我」）——**但这个授权只管「改」**：改状态、降 review、补关键词、拆条、重建索引这类可逆动作不必逐项征询；**永久删除与归档仍按下面 `:33` 那条每条先问**，一句话说清删什么留什么（2026-11-24 对齐：旧授权当时针对的是审议与整理，不含删）。删或改用户本人的事实信息（学业、去向、偏好）同样要谨慎，拿不准就标「待确认」，不硬写。
2. **写入串行**：同一批不要并行发 remember 或 update——并行 `memory_remember` 可能返回同一 id 静默丢内容，或生成重复条目。
3. **只动自己的库**：跨工作区、共享面（`memory_mail` 信箱、共享脚本、别人的库）的改动，当轮 memory_mail post 留痕。

判据：说不清这次属于哪一类，就先只读不写。

- **「长期用不上」看 `last_accessed_at`，不看 `hit_count`**——累计次数会把「周期性使用」误判成热，也会把关键词误命中当成真需求。
- **体检当场修完**，不许只报问题；归档前先问用户，一句话说清删什么留什么。**例外**：用户已经明确说「归档这条」「删掉它」时属已授权，直接做、事后报一句，不必再问一遍。
- **超过 450 字符就该压**（lesson 平均 350 字）；压的时候砍现场叙述，留报错串、路径、判据、指针。
- **字数上限按 content 算，分两档**（2026-11-23 定）：`rules` 与 `lesson` **250 字**，其余层（fact / principle / topic / todo / user / project / soul）**200 字**。分档理由：这两层要带判据、边界与具体数值，砍到 200 会变成空口号；其余多是单一结论。`title` 是写入时自动取 content 首句前 40 字，属派生字段，**不重复计入**（2026-11-22 与 LB 对齐；此前按 title+content 算等于把上限压到 160，会误判一堆合格的条目超限）。**2026-11-23 实测分布**：全局库 63 条活跃，中位 128；`principle` 平均 102（短照样写清），`lesson` 最长 309、`rules` 最长 243——原先「各层同一个数、lesson 也不放宽」的判断因此作废，那批数字是 11-22 的旧样本。超了先拆成两件事，真拆不动再删细节。
- **时间线（事件 / 阶段 / 决定 / 人格性状）不设字数上限**（2026-11-23 用户定）。它们与九层不是一套东西：九层条目要挤进首轮块与检索排名，长度直接影响别人的可见性；时间线只按 persona 隔离、注入里只占「当前处境」一行（事件标题 + 阶段环境标签），长不会挤掉谁。判据：写经历时**先写全**，别为了短砍掉当时的处境与放弃的选项——那两样正是它比结论值钱的地方。压缩发生在注入渲染时（摘要 60 字），不在写入时。
- **压缩时行内代码只脱反引号、保留内容**：里面常是文件名/工具名/配置键，剥掉句子就没主语（`presets/study.patch.yml` 曾压成「StudyHub 的 不只在升级时被覆盖」）；代码块可整删，行内代码不行，识别信号是摘要里出现「的 」「在 被」这类断口。

## 判据不成立时

- 信息不足（不知道原始决定、拿不到采集日期）→ 不写结论；真要留个印象就写 `memory_observe`（过程记录，不进检索、不进全局），别升级成 fact / lesson。
- 涉及用户本人的事实信息 → 先问，或标「待确认」，不硬写。
- 涉及环境级改动（装组件、改 PATH、迁目录）→ 先说清代价，等明确同意。

### 四类任务的最小动作

- **写一条**：查重 → 定层与 project → 串行写 → 回读。
- **改一批**：先导出清单 → 定改动集 → 串行执行 → 回读校验 → 留痕。**先 dry run**——导出清单后先只打印「将改哪些、每条改前改后各一句」，确认命中的是这一类而不是碰巧同名的一批；判据按类型收窄（只改 `status='memory'` 的 lesson、只改某个 project），别拿「内容含某关键词」当唯一条件，那会把同词的别类条目一起扫进去。
- **体检**：直读库 → 四类筛查 → 当场修 → 复算数字 → 报告。
- **迁移**：看现状 → 说清代价 → 执行 → 验记忆系统 → 通知可能受影响的会话。

## 写之前

0. **先判值不值得写。** 下次还会用到、或这次踩过坑 → 写；一次性任务的过程细节、能现查的文件内容、商品事实 → 不写。判据：这条被注入时，除了「哦」还能带来动作吗。
1. **先查重，别急着写。** `memory_search` 用关键词或句子查同义条目；涉及某个项目先 `memory_project('<项目名>')` 拿全景。已有条目能 update 合并就不要新增。
2. **判该不该进记忆库。** 技能＝操作手册（遇到 X 按 1-2-3 做），记忆＝证据与教训（那次为什么失败）。有步骤且会反复用 → 写进技能；事实、坑、一次性教训 → 写记忆；又流程又教训 → 技能写「怎么做」，记忆留「为什么」。已经写成技能的操作步骤，记忆里只留一句指针加技能解决不了的那部分（某次踩坑的具体数字、某个 API 的怪行为），不要把技能正文复述一遍。
3. **确认 project 列表再落笔。** 写前先看已有项目名，别把项目信息错标「全局」；全局适用填「全局」，同一条适用于多个项目时用英文逗号分隔。
4. **串行写并回读。** 一次只发一条写操作；写完 `memory_read` 读回全文，确认 id 与内容都对得上。跨会话约定尤其要回读：光在对话里说等于没发生。
5. **条末附本届会话识别码。** 写 fact、lesson、topic、project、rules 时内容末尾带本会话的码；用别的会话的码比不写更糟。新会话不自动继承旧码，要沿用或新建立必须先问用户。
   - **别给别人的条目补码**：dream 或体检里整理过的跨会话共享条目，它写成的时候不知道本会话，事后补上本会话码＝假留痕，将来查不出它从哪来。只有这条真由本会话产生（或本会话明确承担）才带码；`source_session` 字段同理，填条目的真实来源。
6. **长期约定立刻落库。** 只要出现「以后…都…」「下次你说 X 我就 Y」这类约定，当场写 rules 或 user，不要等另一个窗口来问「没告诉你吗」。
7. **动共享面当轮留痕。** 归档、删除、批量改记忆库，改共享脚本或配置，都属影响共享面的操作：在当轮回信里写清改了哪些条目、影响面、回滚方式，并请对方对称执行；留痕写进自己那份回信文件，不往别人的文件里追加或修剪。

### 两库判据（2026-11-21 定）

记忆库现在分两个库，写入前先判这条该去哪边：

| 库 | 路径 | 放什么 |
|---|---|---|
| 工作区库 | `C:\deepseek\<工作区>\.dsh-mind\memory.db` | 只对这个项目、这台机器当前阶段成立的事 |
| 全局库 | `C:\deepseek\.dsh-mind-global\memory.db` | 换个工作区还成立的本机知识与通用方法 |

判据一句话：**换一个工作区打开，这条还对吗？** 对 → 全局；只对某个项目、某段时间成立 → 工作区。

- 怎么写：`memory_remember` 的 `project` 填「全局」即落全局库（路由看这一列，不靠目录）；其余工具按 id 自动定位，不必自己选库。
- `memory_observe` 永远写工作区——观察是过程记录，不进全局。
- **不许同一事实两边各写一份**（两套真相，对账成本高过收益）；项目状态也不许挂「全局」骗过路由。
- 关系不能跨库：一边全局一边工作区建边会被拒，因为 `memory_read` 的关系与 dream 重建会因此对不上账。
- 读不用管库：`memory_search` / `memory_read` / `memory_context` 自动两库，全局命中带 `[全局]` 标记；`memory_home` 返回两个路径，`memory_health` 给两库合计。
- 回滚：配置里 `globalDir` 设空串 → 退回单库（只读工作区），不报错。

## 写什么层

| 层 | 放什么 | 形态与长度 | 判据 |
|---|---|---|---|
| soul | 只认**全局库**那条（跨工作区人格底色）；**工作区库的 soul 段 2026-11-23 起不再注入**——本会话人格由 `persona_traits` 提供，见首轮块「人格（本会话）」段 | 少用 | 本会话专属的写 persona，跨工作区的底色才写 soul |
| user | 用户基本信息、基础偏好、重要设备与网络环境、关于用户本人的重要事 | 每会话注入，必须短 | 太长会挤掉真正重要的条目 |
| rules | 设计原则与行为准则；全局准则 project 填「全局」，项目特定准则填项目名 | 一条一个准则 | 会被反复违反的才立 |
| fact | 细碎原子事实 | 一句话直陈，≤60 字 | 一条只装一件事 |
| lesson | 学到的经验、被纠正的教训 | 一句话，标 corrected | 被纠正过的一定记 |
| topic | 一件事的前因后果与发展脉络 | ≤300 字，可随发展更新 | 有过程、需要全局视野 |
| project | 项目元信息 | 六个子类，见下 | 只属于某一个项目的信息 |

**人格性状（`persona_traits`）不在这张表里**——它按 persona 隔离、只在该用途的会话间共享，不参与九层检索。判据三条（2026-11-23 定；此前没有任何标准，实测 9 条里 8 条放错层）：

1. **换个用途的会话，这条还成立吗？** 成立 → 不是 trait（进 `rules` 或 `AGENTS.md`）；
2. **它说的是哪一种事？** 「他这个人」→ 画像（`user_profile`）；「我该怎么做」→ `rules` 或 `AGENTS.md`；「在这个用途里我们怎么配合」→ trait；
3. **一条只讲一个特质**，写成「他/我 习惯…」。

**project 六个子类**：

| 子类 | 放什么 |
|---|---|
| overview | 目的、总览、元信息、概括 |
| structure | 架构、目录、模块关系 |
| decisions | 重要设计决策与理由 |
| quotes | 值得保留的用户原话 |
| ops | 端口、路径、启动方式、数据库位置、运维操作——这类是断言「某处是什么」，同样要在 evidence 写清实测方式或出处 |
| todo | 即将要做的任务；完成后标 `review`（退出检索与注入）即视为 done |

**关键词**：每条 8-13 个，反向想「用户 prompt 提哪些词时这条该被捞出」，不用项目名当关键词，优先核心实体、语义中心、专有名词。

**importance**：4＝致命红线、健康安全；3＝用户强调、全局适用；2＝用户决策、跨文件的抽象总结；1＝琐碎原子信息。

**status**：新建默认 `memory`。旧三态名（`active` / `stale` / `archived`）已废，读老数据时这样映射：`active` → `memory`，`stale`（完结）与 `archived`（归档）→ `review`。六态里只有 `memory` 与 `evolution` 进检索与注入；`evolution` 是「更新过的版本」（带版本与回滚点，权重 0.9），**不是「完结」**——完结一律 `review`。取值以下一行为准。
**status 以插件枚举为准（上行为旧三态）**：六态＝`observation`／`evidence`／`candidate`／`memory`／`review`／`evolution`（`evolution` 待退役，别往里写），新建默认 `memory`；检索与注入只认 `memory`／`evolution`，`review` 能 `memory_read` 按 id 回溯但不进 bm25 与注入。用户偏好统一进 `user_profile` 表（分节 + narrative 按轮注入），原 user 记忆整批降 `review` 归档。

**拆分判据**：读一遍能用一句话概括就是一条。出现「另外」「还有」「顺便」多为混装，拆。拆之前先归档原文，顺序见下一节。
**画像边界**：user 层与 `user_profile` 只收跨场景稳定的特质（价值观、沟通风格、交付偏好）；只在某个场景成立的倾向（写卡、解析文档、跑学习流程）归对应技能与准则层，判据＝换一个场景还用得上吗。

### 什么时候写时间线（事件 / 阶段 / 决定）

时间线四表（`episodes`／`phases`／`decisions`／`personas`）与九层不是一套：九层存「结论」，时间线存「那段经历」。**没有自动入口**——`agent/pre-step` 只把用户原话捕获进 `events`（原始档，不进检索、不进注入），事件与阶段必须显式调工具。

| 写什么 | 判据 | 不写 |
|---|---|---|
| 事件 `memory_episode { op:'create' }` | 跨多轮、有明确目标（2026-11-24 用户定，**不要求「持续数周」**——原标准让时间线两库 0 条）；事后能回答「那阵子在忙什么」 | 单轮就能收尾的一次性任务（装个插件、修个 bug）——那是 `lesson`／`fact` |
| 阶段 `{ op:'phase_start', episode_id, env }` | 同一事件里**判断标准变了**（预算、时间、住哪、方向改没改） | 只是进度推进——开新阶段会自动归档旧阶段，为记进度反复开会把真实阶段切碎 |
| 决定 `memory_decision` | 有取舍（选了 A 没选 B），且以后要按它办事 | 单方结论、没有放弃项的选型 |
| 性状 `memory_persona { op:'trait' }` | 换个用途就不成立、但在这个用途里反复出现的配合方式 | 换别的会话照样成立 → `rules`／`AGENTS.md` |

**工具自己会做的别手工补**：`phase_start` 归档该事件上一个未归档阶段、`seq` 自增、写 FTS；`decision` 不给 `phase_id` 就挂该事件最新阶段；`supersedes` 把旧决定降 `review`；`close` 事件归档其全部阶段。

**`env`（场景标签）**：逗号分隔，如 `租房,预算紧,时间充裕`。同一事件内**复用同一套词**——换说法等于换维度，`memory_search { tags }` 就匹配不上。它同时是首轮块「当前处境」那一行的内容。

**先写全再渲染**：时间线不设字数上限（见本文开头长度那一节），当时的处境与放弃的选项正是它比结论值钱的地方，压缩发生在注入渲染时，不在写入时。

**读**：`memory_search { event: '事件 id' }` 收一个事件下的阶段与决定；`tags` 按场景筛（决定继承所属阶段的标签），但它**只过滤时间线条目、九层照常返回**——只想看场景就同时限定 `level:'phase'`（2026-11-24 实测：带 `tags` 不限定层时返回的是九层结果，属于设计不是 bug）。首轮块里「- 事件名｜env」来自这里，那行空着说明没建事件——接手长期任务时先查有没有现成事件，别重复建。

### 写一条时的字段顺序

1. content 先写全，再压到该层的长度上限。
2. keywords 取 8-13 个，含用户可能说出的原话词。
3. importance 按上面的四档定，不确定就从 2 起。
4. project 与子类填准；不确定是全局还是项目，先查已有项目列表。
5. 条末附本届会话识别码，然后 `memory_read` 回读。
- **压长度有系统偏差**：目标 480 字实测落在 598–706（+25%~+45%），要按目标 ×0.75 定；改完立刻复算 `length(content)`，别凭感觉报数——润色删形容词到不了，只能整段砍一个子主题。
6. **正文只写结论与判据，证据另存。** 原话、实测数字、报错原文写进 `memory_remember` 的 `evidence` 参数；`memory_update` 改正文时旧正文自动进 `memory_evidence`，dream 瘦身走的也是这条路；正文按层上限压（fact ≤60、topic ≤300）。
7. **证据必填，不是可选。** `evidence` 参数写清「这条从哪来」：原话片段、报错原文、实测数字，或 `mNNNNN` / `文件:行号`。写事实与教训（fact / lesson）时这一项不能空——落笔前先能回答「这条从哪来」，答不出就别写事实类，改用 `memory_observe` 当观察（观察不进检索，可以模糊）。
   - **证据不全就挂起，别硬判。** 出处只指得到「大概」，或几处证据互相冲突 → `status` 写 `review` 而不是 `memory`，正文里写清缺的是什么。判据：三个月后有人问「这条依据是什么」，能直接读出出处才算 `memory`。
   - **原话与数字照抄，不要转述。** 转述成更顺的句子那一步，就是「把原文没写的塞回去」的开始——这是本地记忆模型那套提示词合同里最贵的一条教训（2026-11-23 从 `qwen3.5-4b-memory-v2` 的抽取合同借来）。
   - **这条为什么值得单列**：它逼你在写之前先定位，而不是先写结论再补理由。先有结论再去凑证据，凑出来的证据会对不上原文。
- **挂起的要回收，不能只挂不管**：进 `review` 的条目正文里写清缺什么，补上证据后用 `memory_update` 带回 `evidence` 并把 `status` 改回 `memory`，它才回到检索面；体检时顺手扫一遍「review 里证据已补全的」，别让它们烂在挂起态。

- 一条只讲一件事；关键词 8–13 个，按「用户会在什么话里提到它」反向拟，别用项目名当关键词。
- 涉及用户原话必须保留措辞；被纠正的标 `corrected`。
- 新建前先 `memory_find_similar` / `memory_search`，高度重复就合并更新，别开新条。
- **整理时同步判去向**：每条问一句「这是方法与流程吗」——是就写进技能、或修正补充已有技能，记忆里只留一行指针；不是（状态、数字、一次性事实、偏好）才留库。两者冲突**以技能为准**（技能是执行面，记忆是结论面），当轮改技能并回写记忆。

## 什么时候删

**先定位到具体条目**：用户说「这条」「那条」时别按标题猜 id——先 `memory_search` 找候选、`memory_read` 确认层与正文，再动手。定位不到就弹卡问是哪条，别猜着改。

先问三句：它有后继事实吗？它属于用户本人的事实信息吗？该拆还是该归档？

1. **归档判据是「有没有后继事实」，不是「内容旧不旧」。** 被取代的版本、被新结论改写的旧结论、重复条目 → 归档；只是「放了很久没用上」不等于过时（那是第 3 条的「长期用不上」，判据不同）。用户说「它过时了」时先确认一句「被什么更新了」——真被取代才归档，单纯旧就留着当过程参考，冲突时以最后更新时间戳为准。
   - **改了结论就当场归档旧条**：这是最危险的一类重复——两条说的不是同一句话而是相反的话（旧的写「四种 kind 都带封面两页」，新的写「固定开销只有一页」），检索时两条都命中、模型各读一半，比同义重复更难发现。判据：本轮 update 若改变了结论，同批把被取代那条改 `review`。
2. **三种动作不要混。** 归档＝status 改 `review`（语义删除：退出检索与注入，但 `memory_read` 按 id 仍能回溯；旧文档里写的 archived 就是现在的 `review`，插件枚举里没有 archived 这个值）；完结＝todo 或 topic 标 `review` 并在正文写清为什么；合并＝保留最新结论那条，其余归档。
3. **「长期用不上」的判据**（2026-11-18 实测）：
   - 看 `last_accessed_at`（最后命中时间），不看 `hit_count`（累计命中）。累计命中高不代表现在还有用。
   - 检索排序用 `updated_at` 算 recency＝`exp(-天数/30)`、权重 0.15；时间戳量级必须是毫秒——写成 17 位微秒会被当未来时间、天数夹成 0、recency 恒 1，整库时效权重失效。
   - 最后命中很近但内容在当前场景无复用 → 是误命中，不能当「有用」的证据。
   - 建龄不满 1 个月且 h=0 的条目不算「长期用不上」的证据：样本太短，先放着。
   - 同时满足「建龄 ≥ 1 个月」「h=0 或 `last_accessed_at` 久远」「无后继引用（技能、准则、其他条目都不指向它）」才进归档候选。
4. **拆分先归档原文，再写新条目。** 顺序反了，新条目会被自动合并回原条目。
5. **同日多批 dream**：动手前先查「本轮已经改过哪些条目」，避免同一批里二次改动。
6. **插件合并或改名后扫全库旧名**：旧包名、旧工具名、旧路径，别留下指向已不存在东西的条目。
7. **需要先问用户的**：删或改用户本人的事实信息；拿不准的条目（标「待确认」而不是猜着写）；跨工作区或共享面的批量删改（先留痕再动）。
   - **不可逆操作先留底**：删、批量改、迁移之前先把现状导出（db 备份或 `handover\` 存档），出事才回得去——留底的成本远低于重建证据链。**单条归档不算**：只改 `status` 不动正文，`memory_read` 按 id 随时能回读，另外导一份是重复劳动。
8. **禁止**：直插别人的 SQLite 库；用文件工具改记忆库本体（读可以，写必须走 `memory_*` 工具）；把归档当删除（`review` 仍可按 id 回读，别丢证据）。

### 合并的标准流程

1. 选主条目：保留最新结论、信息最全的那条。
2. 把被并条的独有事实补进主条，别只做删除。
3. 被并条 status 改 `review`（= 旧文档里的 archived），主条回读一遍。
4. 合并后关键词取两者的并集再删冗余，别沿用被并条的旧关键词。
5. 若在共享面，当轮留痕。

### 按技能去重（2026-11-21 定，用户口径）

用户原话：「先按技能去重，把技能覆盖到的记忆删掉」。技能是执行面、记忆是结论面，同一条判据两处都有就是两套真相。

1. **判据**：这条记忆的核心判据或步骤，能不能在技能原文里读到？能读到且记忆没有额外信息 → 删记忆，保留技能。**必须读技能原文**，关键词召回或「同主题段落」都不算覆盖。
2. **三档判定**：`覆盖`＝技能已写明判据/步骤且记忆无新增；`部分`＝技能提到同主题但缺关键数字、报错串或边界；`零命中`＝整个技能集里没有。只有「覆盖」才删，「部分」先补技能再谈删。
3. **先补技能、再删记忆**，顺序不能反：把技能缺的细节（阈值、报错原文、反直觉行为）插进对应小节、改完 `node --check`/抽读确认，再删记忆。反着做，中途任何中断都会丢内容。
4. **规模大就切片派子代理**：按条号 `i % 4` 分片，每片一个只读子代理只写自己的 JSON（`{n, covered, where, quote, reason}`），主线合并后**自己抽查 3–5 条边界**——打开技能文件对应行核对原文，别信回执。
5. **删前存档**：被删条目的正文先写进 `handover\` 一份（或 `memory_evidence`），便于日后回滚；单事务删记忆 + 标记 + 证据，别一条条删到一半中断。
6. **反例**：只看关键词命中就判覆盖，会把「提到同名词」误删（如把「cron 表达式」误判成「定时任务技能已覆盖」）。

### 批量精修正文（2026-11-21 定）

适用：整库正文偏长、断句坏——机械瘦身会留下「SKILL.md（69 行 / 5,815 B。」这类截断，光靠自动 pass 修不好；用户批准全量重写时才做。

1. 先备份 db（含 `-wal`/`-shm`），再按层导出活跃条目为 JSON 分片（rules / project / topic / fact a-b / lesson a-c），一片一个子代理。
2. 任务书写死：正文＝结论＋判据、目标 80–160 字、**硬上限按层分档**（rules 与 lesson 250 字，其余 200 字，含识别码）、阈值/路径/命令/字段名逐字保留、删实测过程与时间流水、修补残句与未闭合括号、单行无 Markdown、原识别码保留不新增。
3. 子代理只写自己的 JSON 文件，**数据库由主线串行写**——多个进程写同一个 SQLite 会抢锁。
4. **字数必须主线复核**：子代理自报 198 字的条目实测 206–293 字；用 `[...str].length` 过一遍，超限自己改，别信回执。
5. 写入：旧正文先 `addNoteEvidence`（按 `memory_id`+`quote` 去重）→ `UPDATE` 正文 → 重建 FTS。证据表顺带成了回滚来源：早前被截断丢掉的原文能从 note 取回重写。
6. 验收：超上限 0 条（rules / lesson 按 250，其余按 200）、占位符 0、各层字数与均值、抽读 5 条（含一条「数字过时」的，看是否已降级为判据）。

### 用户批改后的处置（2026-11-21 定）

1. 标记在 `memory_marks`（列是 `id`/`verdict`/`marked_at`/`note`，**不叫 memory_id**），不是 status；先按 verdict 统计，别逐条读。
1b. **先看 id 现在是不是 `review`**：`memory_marks` 只增不减，用户连着批改两次时旧标记仍留在表里——120 行里可能有 39 行对应的 id 早已归档。处置前把 marks 和当前 `status` 对一遍，已是 `review` 的跳过，报告里单列「早前已删 N 条」。不做这步会对同一批 id 反复跑 update：无害，但白跑一轮，还会让人误以为这一轮删了很多。

2. 评语三类，处置不同：①「技能里已有」→ 打开技能原文核对，有就删；②「可以放准则里」→ 先写进 AGENTS.md 或全局库 rules，再删；③「过时／环境信息」→ 直接删。
3. 用户标「有用」的一律保留，哪怕内容与别处重复。
4. 删前备份 db；**单事务**删记忆 + 标记 + 证据 + 向量 + FTS，逐条删到一半中断会留半套。
5. 未批改的不动，汇报里写明条数——用户看到「删 232、未批改 171」才知道还有多少没看。

## 体检流程

1. **先 `memory_health` 拿两库合计，再直读 SQLite 逐层看。** `memory_health` 与 `memory_home` 都已按两库统计（工作区 + 全局），直接读库时两处都要读：工作区在 `<工作区>\.dsh-mind\memory.db`（如 `C:\deepseek\work\.dsh-mind\memory.db`），全局在 `C:\deepseek\.dsh-mind-global\memory.db`——只读工作区会漏掉全局那一批。每层一张表：soul、user、project、fact、lesson、topic、rules、todo。只读查询先导出紧凑清单（id、level、字数、摘要），再判问题。
2. **注意列差异**（2026-11-23 实测两库）：九层都有 `project` 列，都能按它路由到全局库；`lesson` 比其它层多一个 `corrected`（13 列 vs 12 列）。查全表时注意 `lesson` 的列数不同，别拿一套 SELECT 套九张表。
3. **四类问题逐个筛**：
   - 错误：与现状冲突、事实已变；
   - 重复：同一结论多份，合并；
   - 已完结：todo 完成、topic 达成目标 → 改 `review`（退出检索与注入，仍可按 id 回读）；
   - 超长：一条装多件事 → 拆（先归档原文）。
   - 另加三类易漏：易腐快照数字（「已装 N 个」「库内 N 条」「现状（某日期）」）、无后继的旧版本结论、证据缺失（fact / lesson 与 ops / structure 的 `memory_evidence` 为空，或只写到「大概」「之前测过」——补出处，补不上就降 `review`）。
    - **rules 层也会过时，且过时得更隐蔽**：用户后来的口头澄清往往只写进了 fact，rules 那条还停在旧说法，而 rules 是每轮注入的——错的那条反而更容易被读到。体检时对每条 rules 问一句「用户后来改口了吗」，改口的并进 rules 正文、再把 fact 归档。
4. **「长期用不上」的候选按上一节判据算**，别只看 h=0；把 `last_accessed_at`、建龄、引用面三个证据一起看。
5. **当场修完，不许只报问题。** 体检的产出是「已修正的库」，不是「问题清单」；发现问题当轮改，改完再报告。
6. **写操作串行，update 核对完整 id。** 短 id 前缀会撞（如 `0mvce0ck` 与 `0mvce0cky`），必须用完整 id 定位。报「未找到该 id」但条目明明在时，先看码位——`0`/`o`、`1`/`l`/`I` 在等宽与比例字体下都可能分不清，用 `repr` 或 `[hex(ord(c)) for c in id]` 逐字符核一遍再重试（2026-11-21 实测卡半小时：第 7 位是字母 `o`，不是数字 `0`）。
7. **收尾三件事**：回读校验改动；复算规模（active 条数、总字数、归档条数）并带采集日期；给一句回执。例：`2026-11-18 体检：405→370 active，147.1K→127.1K 字，归档 35 条`。需要用户裁决的单独列，不混在回执里。
8. **哨兵**：顺手确认记忆系统本身可用——注入横条可见，`memory_search` 能返回结果。坏了当场说，别等用户发现。
9. **有跨工作区或共享面改动的**，按「写之前」第 7 步留痕，再给报告。

### 记忆验收（干完怎么算对）

写/改记忆——**四条**：①`memory_search` 能用关键词召回这条，内容正确；②keywords 是 8–13 个、project 标签对；③与新条目重复的先合并而不是新增；④fact / lesson 与 project 的 ops / structure 子类，`evidence` 非空且指得到具体位置（原文片段、命令输出、`mNNNNN`、`文件:行号`），不是「大概是这样」。

记忆体检——**四条**（对应自检的待人工对账）：①按层条数与字数、超长条目清单都看过；②四类问题（错误 / 重复 / 已完结 / 超长）逐条判过，不是只报数字；③改动当轮落库并用 sqlite 复验；④报告写清改了几条、为什么保留没改的。

## 索引重建（2026-11-22 定）

**什么时候必须重建**：批量改过正文（`memory_update` 只写正文，**不重算向量**）；把条目从一个库搬到另一个库；换 embedding 模型或 dtype；检索突然大面积搜不到（先怀疑索引，别怀疑词）。

**脚本**：`scripts\rebuild-index.mjs`。用 runtime 的 node，别用系统 node——要 `node:sqlite`。先设一次 `$node`（下面命令里用的就是它）：

```powershell
$node = 'C:\Users\ZQY\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe'
```

```powershell
$env:ELECTRON_RUN_AS_NODE='1'
& $node C:\Users\ZQY\.agents\skills\memory-collab\scripts\rebuild-index.mjs                    # 全局库
& $node C:\Users\ZQY\.agents\skills\memory-collab\scripts\rebuild-index.mjs <工作区>\.dsh-mind\memory.db
& $node ...\rebuild-index.mjs <库> <meow-mind 目录>                                             # 插件不在默认位置时
```

**两条口径抄错就静默搜不到**：

1. `memory_fts` 的 body 必须走 meow-mind 自己的 `buildBody(title, content, keywords)`——中文连续段取 2-gram 滑动、单字保留、英文数字按 `[A-Za-z0-9_.+\-/#@]` 成词、keywords 拼两遍加权、上限 400 token。按空格切或用 SQLite 默认分词器写进去，看似成功，查询时 `ftsQuery` 包成 `"..."` 短语会对不上，返回空且不报错。
2. `memory_vectors` **先整表 `delete` 再写**。只 upsert 会把已归档条目的旧向量留成孤儿，自检「向量条数 = 活跃条数」永远对不上（2026-11-22 实测全局多 3 条、工作区多 658 条，第一遍跑完全绿之外全 FAIL）。

**验收**：末行必须是 `PASS`（`active = fts = vectors`，且 `异模型 = 0`）；再挑一个「只在重建后才存在」的词跑一次 `memory_search`，命中才算完。只信 PASS 不看检索，等于只验了计数没验通路。

3. **生效时机（判据）**：改完 → 下一次成功文件操作后，对新请求生效；已经开着的会话不追溯；想立刻看到就开新会话。成功的 read/write/edit 触达更深目录时会补注入新适用文件，删除或变更也发通知，会话 resume 会重对基线。
4. **全局 rules 只在会话开始注入一次**：中途新增的 rules 不会自动出现。用户改完规则问「读到了吗」，必须主动 `memory_search` 或查库确认，不能凭「应该注入了」回答。
5. **改准则文件的顺序**：先改完整版 → 再同步要点版 → 对拍结构（节号、节数、口径）→ 查易腐数字 → 回读行数与字节数 → 需要时当轮留痕。
6. **工作区隔离**：记忆库是工作区级，每个工作区一个 `.dsh-mind\memory.db`，互不相通。写给别的工作区的规则，写进全局库 `rules`（`memory_remember` 时 `project` 填「全局」）或补进 `memory_doc` 的样板；不要再写本地 md 文件——各工作区读不到，也不随注入生效。
7. **新增共享工具**：先补完整版，再回填要点版，不要只写进自己工作区的记忆。

### 改一条准则前的四个问题

1. 它是全局适用还是单项目？全局 → 完整版与要点版都要动；单项目 → 写进该项目的 rules 记忆。
2. 它和现有条目冲突吗？冲突先合并成一条，不要两条并列。
3. 它是可执行判据还是口号？写不出「遇到 X 就做 Y」的不立。
4. 改完谁来读？另一个会话要用的，必须落文件加指针，不能只写在自己库里。

## 迁移红线

1. **先分清两个东西**：
   - 记忆库本体：各工作区 `.dsh-mind\memory.db`（如 `C:\deepseek\work\.dsh-mind\memory.db`），按工作区独立。
   - 全局数据目录：日志、梦境窗口账本等实例级数据；`memory_home` 管的是这个。
   - 「把记忆库搬出 C 盘」与「改全局数据目录」是两件事，别用错工具。
2. **`memory_home` 用法**（2026-09-25 实测于 0.29.0，版本以插件实时为准）：不带参数＝只查看；带 target＝解析、迁移、热切换（后台异步搬移，不重启、不重载插件）。三个预设：default（系统用户主目录）、dsh-storage、plugin-root，也可传任意绝对路径。
3. **三条红线**：
   - 目标非空视为已迁移，绝不覆盖；
   - 旧目录任何情况下不自动删（跨盘复制时旧目录保留，删不删由用户确认）；
   - 同盘 rename 优先，跨盘降级为递归复制，搬完落标记文件（2026-09-25 记录为 home-dir.json，文件名以实时行为为准）。
4. **拒绝的路径**：空、相对路径、盘根、主目录本身。
5. **迁移后验收**：`memory_search` 能读旧库；`memory_*` 工具都在（meow 升级后可能从 `dsh.profile.bundles` 掉出，表现为所有 memory 工具报 unknown tool）；确认插件仍在加载。
   - **迁移后三查**（条数相同也可能搬错）：①按层条数（927 vs 927 也可能同数不同物）；②逐条内容与源库比对；③字段级归属分布——七层表漏建 `project` 列时条数全对、归属全空，靠 project 分布（dsh 197 / 全局 32 / gxu-grad 29）才查出。
6. **动手前说清代价**：体积、是否需重启、旧目录留不留，等用户明确同意再动；迁移属环境级改动。
7. **多实例共享同一目录时**，改之前提醒其他实例同步修改，否则一边搬一边写。

## 技能写作纪律

1. **分工**：技能＝操作手册（description 匹配、主动加载、可写长），记忆＝证据与教训（关键词被动命中、每条短）。有步骤且反复用 → 技能；事实、坑、一次性教训 → 记忆；又流程又教训 → 技能写「怎么做」，记忆留「为什么」。技能里不复述某条记忆的内容，记忆里不重复技能正文。
2. **触发词不重叠**：同一件事别让两个技能都命中，否则两个都加载、内容互相打架。写前看现有技能清单，description 的触发场景要有区分度。
3. **description 必须写「名字 + 一句话用途 + 触发场景」**，60-120 字，说清「什么时候该加载它」；只报总数不合格。
4. **自包含**：有脚本的技能，SKILL.md 旁边放 `scripts/` 与 `DEPENDENCIES.md`，不要把关键路径写成外部绝对路径（`C:\deepseek\tools\...`）——换工作区或新会话就跑不起来。只写方法的技能不强行造 scripts。
5. **不写死会腐的数字**：「已装 N 个」「库内 N 条」「现状（某日期）」几个月后就是误导源。要么写成「以 X 实时为准」，要么明确标成历史记录。
6. **实测数字必须带采集日期，并给一条实时刷新命令**（如 `pip list`、`Total-Results` 头、`mineru --version`），否则两个月后会被当成假现状。
7. **边界**：技能只写方法，不写某条具体记忆的内容；不写「详见记忆库 xxx」这类指针，技能要能独立读懂。DSH 插件的装、升、修不进本技能，走 `dsh 技能`。
8. **写完验证**：路径都存在；命令实跑一遍；行数与字节数写进交付说明；触发场景在 description 里一眼能找到。
- **定长度上限前先量本机分布**：跑一遍条数与长度统计，按 P90 或实测最大值定线，并写明样本与日期；说不出阈值出自哪次实测就是照搬，换个库会大面积超标或全不超。

### 什么时候该升级成技能

- 同一套做法第二次重复 → 写技能；一次性的流程不写。
- 会跨工作区、跨会话用到的才写用户级技能，单项目临时步骤留在项目里。
- 写之前先看相邻技能，触发词撞车就合并或划界，别让两个技能同时被拉起。
